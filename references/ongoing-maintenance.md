# 接入后的长期维护

首次接入完成之后，环境仍然会因为升级、换网络、改配置、装新工具而漂移。这份文档只处理**本机环境泄漏风险**的长期维护：出口、DNS、IPv6、WebRTC、进程旁路、工具输出。

账号注册、订阅购买、KYC/身份验证、Claude Desktop 使用、平台风控与封禁处理不在本 skill 范围内；这里也不承诺任何平台检查会通过。

## 1. 先确认哪份配置在生效

Claude Code 的配置目录可以由 `CLAUDE_CONFIG_DIR` 指向别处。存在多个配置目录时，`~/.claude/settings.json` 可能不是生效文件。

- 改权限、hooks、模型、环境变量之前，先确认当前配置目录。
- 读对应目录里的 `settings.json`，不要只改“看起来像配置”的那个文件。
- 改完重开会话；大多数设置不会热加载。
- 如果有多套配置，先确认这次要改哪一套，是一次性还是全部。

## 2. 核实真实启动链

日常入口可能不是二进制本身，而是包装脚本、启动器或沙盒包装，最后才 exec 到实际版本文件。

- 升级通常只替换版本文件，入口和包装层是否仍然生效要单独验证。
- 更新后至少确认：入口能启动、版本正确、网络策略仍然套在真实进程上。
- 不要假设“入口路径没变”就等于“启动链没变”。

## 3. 代理/TUN 与进程沙盒是两层

两者目标不同，不能互相替代：

- **代理/TUN** 决定出站走哪条路径、从哪个出口出去。
- **进程沙盒** 决定这个进程能不能发起未授权的直连。

沙盒不会隐藏本地文件、环境变量、网卡地址和主机信息。开了代理不代表本地标识不可读；反过来，套了沙盒也不代表出口一定正确。

策略通常只对**新进程**生效。改完规则后，已有会话要退出重开才能验证。

## 4. 验证到进程，而不是验证到配置

只看配置文件、只看代理端口在听、只看健康状态为 true，都不够。

一次完整的验证至少包括：

- 公网 IPv4 直连被拒；
- 公网 IPv6 直连被拒；
- 未授权的 UDP 出站被拒；
- 回环代理可用；
- 代理管理接口按预期被拒；
- 真实业务进程确实继承了这层限制。

如果平台提供进程级沙盒检查，直接对真实进程确认“出站受限”，不要只检查启动器。健康状态只说明探测服务认为出口正常，不等于当前会话已经被限制。

## 5. 固定出口要有可观测基线

把“预期出口”和“健康状态”变成可查的文件或记录，而不是靠记忆：

- 记录预期出口地址，以及它对应的地区/ASN 类型；
- 记录健康探测的最后更新时间、失败次数；
- 用多个独立端点交叉核对出口，不要只信一个 IP 查询页；
- 整机 TUN 下，沙盒内外出口可能相同；“出口相同”不能单独证明沙盒生效，直连被拒才是证据。

出口变化时，先暂停敏感操作，再查节点、规则命中、DNS 和实际出口，保留脱敏后的诊断信息。

## 6. 直连白名单要显式

局域网、SSH、Mesh VPN、远程桌面这类低延迟路径通常需要直连。要明确写清：

- 哪些目标或进程故意不走代理；
- 它们是按进程、域名还是地址段匹配；
- 直连应用会看到真实公网出口，这是设计结果，不是泄漏；
- 直连应用是否还监听了公网地址或局域网地址，入站暴露面是否可接受。

不要在没记录的情况下临时加一条 `DIRECT`，否则下次排查会误以为代理失效。

## 7. 工具输出脱敏是缓解，不是边界

用 PostToolUse 类钩子改写工具结果，可以把公网 IP、出口地区、ASN 等字符串替换掉，降低“模型看到真实出口”的概率。它通常覆盖不到：

- 私网地址、Mesh 地址；
- 主机名、硬件型号；
- 新的、不在名单里的地址；
- base64、拆段、字段提取、写文件再读等派生形式。

服务或钩子失败时可能 fail-open，原始输出会继续传给模型。把它当作降低误暴露的缓解层，不要当作安全边界；真正的边界是权限、最小工具集和沙盒。

## 8. Agent 有 shell 时的本地暴露

只要 Agent 能执行命令，它就可能读到 SSH 环境变量、网卡地址、主机名、硬件型号。这些信息只有在命令输出进入对话时才会到模型。

先把威胁模型分清：

- 关心的是“API 请求的出口 IP”，还是“工具输出里的本地标识”？
- 前者由代理/TUN 决定；后者由权限和输出处理决定。
- 禁一个 `ifconfig` 不能解决问题，同类信息还能从别的命令、脚本或语言运行时读出来。

优先做最小权限、限制不必要的命令、对输出做脱敏；不要用一份很长的命令黑名单冒充边界。

## 9. Skills 与插件要有生命周期

库目录、索引文件、Agent 自动发现的技能目录是三件事。

- 默认装到哪里、是否登记索引；
- 是否允许软链到自动发现目录；
- 是否关闭官方账号的技能/插件自动同步；
- 记录来源、版本和许可证；
- 移除时同时清索引和入口，避免死链。

链接策略要写清楚。默认不建软链时，不要因为“想让 Agent 发现”就临时加一个。

## 10. 外部账号/路由工具

Orca、Paseo、CCBaga 这类工具可能同时改配置目录、启动进程、切换账号、操作钥匙串或共享目录。使用前要弄清它改的是哪一层：

- 只改配置目录，还是也改启动入口；
- 切换时会不会结束正在运行的进程；
- 钥匙串里的凭据是按账号隔离还是共享；
- 共享的技能、插件、指令目录会不会被搬走或清空；
- 切换后哪些设置需要重开会话才生效。

切换前先备份，切换后重新核对配置目录、凭据、共享目录和网络策略。不要把“切换成功”当成“所有层都一致”。

## 11. 多账号（可选）

只有在用户明确提出时才展开。通用的原则：

- 每套账号使用独立的配置目录和独立登录态；
- 明确哪些资产共享（指令、技能、插件），哪些必须隔离（会话、凭据、缓存）；
- 同一个会话不要被两个账号同时写；
- 切换工具可能只改其中一层，其余层要单独确认。

具体目录、账号名和映射关系属于使用者自己的配置，不写进本 skill。

## 12. 变更账本与恢复

每次改动至少留下：

- 改了什么、为什么改；
- 备份位置；
- 验证命令和结果；
- 回滚方法。

恢复时按对象局部回滚：配置回配置、网络规则回网络规则、凭据回凭据，不要整目录覆盖。

共享服务需要区分“重载”和“重启”。重载通常不打断会话；重启会。不要为了修一个配置去重启正在承载其他会话的服务。

## 13. 环境自检

把下面几项作为定期检查，而不是一次性验收：

- 出口地区是否仍在支持范围；
- ASN 类型和 IP 信誉是否有明显变化；
- DNS 是否仍经代理解析；
- IPv6 是否仍不会绕过代理；
- WebRTC/STUN 是否仍受控；
- 系统时区、语言与出口地区是否一致；
- 同一设备上是否存在多个账号共用同一环境。

只记录观察结果和观测方式。这些检查用于发现环境漂移，不用于推断平台内部规则，也不保证账号状态。
