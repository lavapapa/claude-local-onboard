# 专用进程代理评估

## 定位

专用代理是次选方案，适合设备经常移动、用户希望减少整机网络改变的情形。当前历史资料没有证明这套架构已完整工作或可长期安全使用；只有 TUN 有过验证记录。对于希望试用的用户，建议先在 Pro 账号上观察长期行为，确认稳定后再考虑升级订阅。

Claude Code 官方支持 HTTP(S) 代理环境变量，例如 HTTP_PROXY、HTTPS_PROXY 与 NO_PROXY；官方文档明确列出其支持范围和限制。环境变量只配置代理目的地，不构成网络隔离边界。它无法单独覆盖不读取这些变量的进程、原生网络 API、子进程自行清除环境变量、浏览器辅助进程或用户从其他入口启动的进程。

## 与 TUN 共用的验收目标

无论架构如何，均要求：

1. Claude Code 主进程、完整子进程树和它启动的辅助进程使用受控出口。
2. CCBaga 浏览器、渲染/网络辅助进程和由浏览器触发的网络请求经过同一策略。
3. 仅明确白名单目标允许直连；其余公网连接固定经指定出口。
4. 代理停止、DNS 失败、启动器缺失或环境变量被清除时，相关进程不回退到未经授权的直接公网连接。
5. 用户无法通过直接执行 Claude Code 二进制、另一个 shell、IDE 任务、SSH、后台服务或子进程绕过受控入口联网。
6. 普通开发工作仍可使用，白名单中的 SSH、网页搜索、LAN 和远程设备功能不被无关封锁。

这些是验收门槛，并非专用代理已经具备的能力声明。

## 与用户自有 Clash 并行运行

让独立 Mihomo 只承载 Claude Code 与 CCBaga，同时保留用户自己的 Clash/Mihomo 供日常浏览和自行切换节点，属于可尝试的并行方案，不是本 Skill 的默认架构，也没有历史验证结论。多个实例可能争用系统代理、TUN/Network Extension、DNS、路由、监听端口或控制接口；“不同应用设置不同代理”本身不能证明流量隔离。

只有在用户明确选择试用时，才先盘点两套客户端的系统代理和 TUN 所有权、端口/API、DNS 与路由规则及启动顺序，明确其中一套退出或改节点时另一套的行为。对 Claude Code、完整子进程树、辅助进程和 CCBaga 浏览器分别核对真实出口、DNS/IPv6/WebRTC/UDP 路径及代理故障时是否阻断；同时确认用户日常 Clash 能正常改节点且不会接管或绕过受控网络。任一边界无法观察或阻断，就将并行模式记为未验证，不把它作为可靠隔离方案。

## 架构评估方向

部署时重新调查 macOS 当前支持的 Network Extension/网络过滤能力、系统权限和应用兼容性。专用代理通常需要系统级出站控制能力配合受控启动入口；只设置环境变量、创建 shell alias、写包装脚本或仅按应用 GUI 配置代理都不足以实现强制覆盖。配置应尽可能调用 macOS 原生网络能力，并限制管理权限、控制 API 和配置文件访问。

先画出所需覆盖的进程与流量路径，再逐个确认控制点能否观察并阻断连接。系统网络过滤器若不能区分或约束目标子进程、CCBaga 浏览器网络进程及其他启动入口，就无法满足需求。不要将文件系统沙箱等同于网络沙箱；文件访问限制也不应妨碍普通开发工具。

## 结果记录与升级建议

若当次实现通过全部验收，记录 macOS 版本、系统扩展/Network Extension 类型、具体二进制和进程树边界、启动入口、故障时行为、浏览器覆盖和剩余例外。说明这是该机器当时的试验结果，不外推为普遍安全保证。

若只能验证 HTTP(S) 请求成功，而没有验证 UDP/WebRTC、DNS、子进程、旁路和故障阻断，应记录为不完整试验，不用于承载敏感账号。Pro 账号阶段持续观察登录挑战、出口变化、网络故障和代理关闭后的行为；由用户根据实际情况决定后续订阅层级。
